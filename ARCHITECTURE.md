# Архитектура CablePlan

CablePlan работает в двух режимах: локальном (React + TypeScript + Vite; Node.js 24 + Express + встроенный node:sqlite) и статическом для GitHub Pages (только клиентская сборка). Общая модель проекта, расчёты и интерфейс используются в обоих режимах; различается только хранение данных, а экспорт CSV/XLSX/PDF выполняется на клиенте в обоих режимах.

## Режимы работы

**Локальный.** Один процесс API хранит SQLite и исходные PDF в `data/`. Координаты — неизменяемые единицы страницы PDF (points); `floor.metersPerUnit` переводит их в метры. Высоты и запасы — метры. UI zoom не входит в расчёты. Доступны серверное хранение, резервная копия JSON с исходными PDF и восстановление; экспорт CSV/XLSX/PDF выполняется на клиенте и от сервера не зависит.

**Статический (GitHub Pages).** Сайт собирается Vite и работает без бэкенда. Публикация — вручную;
это та же сборка, что упакована в APK. Приложение полностью офлайн, без `INTERNET`. Наличие API проверяется запросом `GET /api/health`; если он недоступен, включается режим хранения «Браузер». Проекты сохраняются в `localStorage` (ключ `cableplan:projects`), исходные PDF — в IndexedDB (база `cableplan`, хранилище `pdfs`), поэтому лимит 5 МБ не действует и доступны большие чертежи. Этаж ссылается на файл как `idb:<key>`; демонстрационный план хранится как `data:` URL. Экспорт CSV, XLSX и PDF журнала, а также JSON-копия с PDF выполняются на клиенте (pdf-lib + SheetJS 0.20.3, PDF — со встроенными сабсетами PT Sans/AnOOPlan Sans); APK использует тот же статический режим. В локальном режиме используется хранение «Сервер», в статическом — «Браузер».

## Общая модель (src/model.ts)
```ts
interface Point { x:number; y:number }
interface Floor { id:string; name:string; elevation:number|null; metersPerUnit:number|null; pdfId?:string; page:number; width:number; height:number }
interface Equipment { id:string; number:string; name:string; type:string; floorId:string; x:number; y:number; height:number|null; note:string; properties:Record<string,string>; color?:string|null }
interface Vertex { id:string; floorId:string; x:number; y:number; height:number|null }
interface Segment { id:string; a:Vertex; b:Vertex; mode:'orthogonal'|'spatial'; reservePercent:number; reserveFixed:number; trayWidthMm?:number|null; trayHeightMm?:number|null; trayAreaMm2?:number|null }
interface Dimension { id:string; fromId:string; toId:string; note?:string }
interface Route { id:string; number:string; type:string; segments:Segment[]; note:string; color?:string|null; trayWidthMm?:number|null; trayHeightMm?:number|null; trayAreaMm2?:number|null }
interface Cable { id:string; number:string; name:string; brand:string; purpose:string; fromId:string; toId:string; segmentIds:string[]; reservePercent:number; reserveFixed:number; startReserve:number; endReserve:number; quantity:number; note:string; outerDiameterMm?:number|null; crossSectionMm2?:number|null }
interface Pin { id:string; number:string; floorId:string; x:number; y:number; comment:string; status:'open'|'closed'; photos?:string[]; createdAt:string; updatedAt:string }
interface PriceItem { id:string; kind:'equipment'|'cable'|'tray'; name:string; unit:string; price:number|null; note:string }
interface ProjectEstimate { laborPercent:number|null; note?:string }
interface ChangeEntry { id:string; version:string; date:string; author:string; description:string }
interface ProjectDocument { compiledBy?:string; checkedBy?:string; date?:string; organization?:string; object?:string; documentCode?:string; city?:string; title?:string; changeLog?:ChangeEntry[] }
interface Project { schemaVersion:1|2; id:string; name:string; floors:Floor[]; equipment:Equipment[]; routes:Route[]; cables:Cable[]; pins:Pin[]; dimensions?:Dimension[]; updatedAt:string; document?:ProjectDocument; catalog?:PriceItem[]; catalogDate?:string|null; estimate?:ProjectEstimate }
```

Сегменты связаны совпадающими координатами и этажом с допуском 1e-6; height также совпадает. Кабель содержит упорядоченный список ID сегментов, каждый физический сегмент допускается один раз. Направление сегмента определяется обходом цепочки. Концы кабеля должны совпадать в плане с началом/концом цепочки на соответствующем этаже; вертикальные подводы от высоты оборудования до высоты трассы учитываются отдельно. Межэтажный сегмент разрешён только при совпадающих x,y (общая система координат этажей), учитывает отметки полов. Неизвестные высоты/масштаб и разрывы означают неполный расчёт; итог null.

Формула: G = сумма пространственных длин сегментов + вертикальные подводы концов. Rт = сумма(Lсегмента × %сегмента / 100 + фиксированный запас сегмента). Итог = G + Rт + G × %кабеля / 100 + фиксированный запас кабеля + запас начала + запас конца. Количество кабелей умножает итог только в спецификации. Инфраструктура учитывается однократно. Промежуточные результаты не округляются. Ортогональный сегмент не допускает одновременных изменений x,y; горизонтальное и вертикальное движение — сумма, spatial — гипотенуза.

## Типы КНС, цвета и заполнение

Кабеленесущая система (КНС) задаётся свободным `Route.type`; `src/route-kinds.ts` распознаёт четыре
готовых типа — **лоток**, **гофра**, **труба**, **кабель-канал** — по подстрокам («лоток», «гофр»,
«труб», «кабельный/кабель-канал», «короб») и не требует менять схему. Для типа определены цвет по
умолчанию (`#008e94`, `#e78c22`, `#2f6fda`, `#2f9e63`), способ сечения (прямоугольник Ш×В или круг по
диаметру) и подписи. Свой тип получает нейтральный цвет. `Route.color` — необязательный `#rrggbb`
(нормализуется как цвет оборудования), `routeColor(route)` возвращает сохранённый валидный цвет или
цвет типа; цвет используется на плане (CSS-переменная `--route-color` у SVG-группы), в списке трасс,
легенде и `plan-svg.ts` для PDF-листа «План», поэтому выбранный/подсвеченный сегмент по-прежнему
отличается цветом выделения. Валидация API отклоняет некорректный `route.color` (422).

## Схема трасс, углы и размеры

`routeSummary(project)` из `src/engine` (реализация — `src/engine/routes.ts`) даёт строки по трассам (длина, число сегментов, углы,
метраж по эффективным сечениям — `sections`) и итоги по типам КНС: лоток, гофра, труба, кабель-канал,
свой тип. Длина — сумма `segmentLength`; `routeSectionLengths` группирует сегменты по эффективному
сечению (`segmentSectionLabel`), `routeSectionsText` печатает «100×50 — 12,4 м; Ø25 — 3,1 м».
`routeAngleStats` считает изменения направления на стыках соседних сегментов (90°/45°), для коробов
это количество углов. Лист «Схема трасс» (PDF/XLSX/CSV) и раздел «Схема трасс» в «Ведомостях» строятся
по этой сводке; фитинги и крепления не считаются по решению владельца.

`Route.subsystem` (горизонтальная / магистральная / рабочее место) — необязательная подсистема СКС;
`specificationKnS(project)` агрегирует **каждое эффективное сечение** по подсистеме и типу, добавляет
углы коробов и артикулы/производителей из справочника цен (`PriceItem.article/manufacturer/series/size`).
Если в одной трассе разные лотки/трубы, её метраж входит отдельными строками по сечениям; углы коробов
считаются один раз и относятся к основному сечению (наибольший метраж), чтобы не задваиваться.
`suggestRouteSection(project, route)` подбирает минимальное стандартное сечение по фактическому
заполнению (≤40 %) и диаметру кабелей, но учитывает только сегменты **без** собственного сечения;
для сегмента с переопределением есть `suggestSegmentSection(project, route, segment)`. Фитинги и
крепления не считаются.

`Dimension` — размер между двумя объектами оборудования: `dimensionGeometry` считает расстояние
по прямой на одном этаже (единицы PDF и метры по `metersPerUnit`), `dimensionText` форматирует
мм/м. Размеры хранятся в проекте, рисуются на плане (SVG) и в PDF-плане; при перемещении
оборудования пересчитываются. Это не длина маршрута кабеля.

`cableSection(cable)` принимает площадь внешнего сечения: `crossSectionMm2`, если задана и положительна, иначе `π·d²/4` от `outerDiameterMm`. Заданное некорректное значение (0, отрицательное, NaN/Infinity) даёт ошибку и `null` — второй источник не подставляется, чтобы неверные данные не выглядели расчётом; если не задано ничего, площадь тоже `null` (данных нет).

`trayFill(project)` идёт по всем сегментам всех трасс в порядке проекта. **Эффективное сечение участка**
считается по полям: заданное поле сегмента (`Segment.trayWidthMm/trayHeightMm/trayAreaMm2`) переопределяет
одноимённое поле трассы, незаданное наследуется. Поэтому в одной трассе допустимы разные лотки/трубы:
`segmentSectionLabel(route, segment)` показывает «100×50», «Ø20» или «S=500 мм²», а `overridden` отмечает
сегмент со своим сечением. Площадь сечения: `trayAreaMm2` (приоритетно), иначе для гофры/трубы —
`π·d²/4` по внутреннему диаметру в `trayWidthMm`, для лотка/короба — `trayWidthMm·trayHeightMm`;
некорректные заданные размеры дают `null`, а не 0. Для круглых КНС высота борта не используется и в
ведомость не попадает. Занятая площадь сегмента — сумма `площадь кабеля · quantity` по кабелям, чей
`segmentIds` содержит сегмент. Заполнение = занятая площадь / площадь лотка · 100 %. Статусы: `ok` (≤ 40 %),
`warning` (> 40 %), `over` (> 50 %), `empty` (кабелей нет), `incomplete` (неизвестен лоток, сечение или
количество). Неизвестные значения не заменяются нулём; `complete` ложно, если есть `incomplete`, а
`maxFillPercent`/`overSegments` дают сводку. Предупреждения вида «Трасса Т1, сегмент Т1.1: заполнение
63 % — превышен предел 50 %» попадают в `domainWarnings` и PDF. Неверное сечение трассы предупреждает
один раз на трассу, неверное сечение сегмента — на сегмент; если все сегменты переопределены, размеры
трассы на заполнение не влияют. `specifications(project).trayFill` — строки по сегментам с эффективным
сечением для ведомости/PDF/XLSX/CSV, в `infrastructure` — `maxFillPercent` и `overSegments` по типу трассы.

Трассы печатаются в PDF цветом типа/своим цветом: SVG-оверлей плана и экран используют один и тот же `routeColor`, поэтому документ совпадает с экраном. Порог 40 % — рекомендуемый, 50 % — предел; сравнение с границами идёт с допуском 1e-9, чтобы ровно 40 % не становилось вниманием из-за погрешности double, а ровно 50 % — превышением.

## Автопрокладка маршрута

`findRoute(project, fromId, toId)` из `src/engine` (реализация — `src/engine/geometry.ts`) возвращает `{ segmentIds:string[]; error?:string }`. По начерченным сегментам строится взвешенный граф: узел — вершина трассы, ключ включает `floorId` и координаты x,y (округление до 0,001), высота на связность не влияет, вес ребра — физическая длина сегмента из `segmentLength`. Для каждого устройства ищется ближайший узел на его этаже по расстоянию в плане, после чего алгоритм Дейкстры находит кратчайший по длине путь и восстанавливает порядок сегментов. Если трассы нет, узлы совпали или граф разорван, возвращается ошибка. Найденную цепочку можно скорректировать вручную кликами по сегментам. Автомаршрут вызывается кнопкой «Автомаршрут» и при выборе двух устройств инструментом «Кабель».

## Цепочка и привязка концов

`chainEnds(project, segmentIds)` возвращает `{ start:Vertex; end:Vertex } | null`. Функция проверяет, что выбранные сегменты образуют непрерывную цепочку в прямом или обратном порядке, и определяет её начало и конец с допуском 1e-6 по этажу, x, y и высоте. Эти концы используются расчётом концевых подводов и интерфейсом.

При создании кабеля концы цепочки автоматически привязываются к выбранному оборудованию: если ближайший конец находится не дальше 100 единиц PDF, оборудование переносится в координаты этого конца (и на его этаж), а направление цепочки выбирается по ближайшей паре «устройство — конец». Если концы слишком далеко, кабель не создаётся и выводится предложение соединить трассу с устройствами. Концевые запасы начала и конца задаются отдельно и входят в итог.

## Учебный проект

`demoPlanPdf()` в `src/demo.ts` генерирует синтетический векторный PDF-план (1000 × 700 единиц): наружные стены, коридор, комнаты, дверные проёмы и подписи стандартным шрифтом Helvetica. Файл собирается в браузере без внешних ресурсов и возвращается как data URL `data:application/pdf;base64,…`. `createDemoProject()` использует его как подложку этажей; проект помечен как учебный и не заменяет рабочую документацию. В учебном проекте у кабелей задана цена (38 ₽/м для КВК-П 2×0,75), поэтому смета и стоимость в журнале/PDF/XLSX считаются сразу, а на плане есть камера, шкаф и розетка с разными иконками.

## Иконки оборудования

Тип оборудования определяет иконку: `equipmentIcon(type)` в `src/equipment-icons.ts` ищет подстроки «камер», «шкаф», «розет», «коммутатор», «считыв» (регистр не важен) и иначе возвращает универсальный маркер. Геометрия всех иконок — `EQUIPMENT_ICON_GLYPHS` в системе 24×24, контуры заливаются цветом с `fill-rule="evenodd"` (объектив камеры, окно шкафа, гнёзда розетки и порты коммутатора — сквозные отверстия). Один и тот же набор используется на плане в `App.tsx`, в списке объектов и в `plan-svg.ts` для PDF-листа «План».

Цвет иконки хранится в `Equipment.color` как `#rrggbb`; `equipmentColor()` возвращает валидный сохранённый цвет или цвет по умолчанию для типа (`EQUIPMENT_ICON_DEFAULT_COLORS`: камеры тёмные, шкафы фиолетовые, розетки оранжевые и т.д.). `normalizeEquipmentColor()` принимает `#rgb`/`#rrggbb` (приводит к нижнему регистру и полному виду), а мусор возвращает как `null`: при загрузке проекта такое значение отбрасывается в `undefined`, при сохранении через API — отклоняется с 422. Невалидный цвет не подменяется молча: при загрузке мусор отбрасывается в `undefined`, и рисуется цвет по умолчанию для типа; через API такое значение отклоняется. Пользователь выбирает цвет из палитры `EQUIPMENT_COLOR_PRESETS`, произвольным `input type=color` или сбрасывает кнопкой «По умолчанию» (`color: null`). Цвет входит в JSON-копию и снимки версий, как и остальные поля оборудования.

## Справочник цен и смета

Справочник цен — часть проекта (`Project.catalog`): позиции вида `equipment` (модель оборудования), `cable` (марка кабеля) и `tray` (тип трассы) с ценой за единицу. Он входит в JSON-копию, снапшоты и офлайн-хранилище, поэтому старые снимки сохраняют свои цены: смена прайса в текущем проекте не пересчитывает историю. `Project.catalogDate` (YYYY-MM-DD) фиксирует дату актуальности прайса и печатается в смете и коммерческом предложении. `normalizePriceItem`/`normalizeCatalog` в `src/estimate.ts` нормализуют записи: цена — `null` при нечисловом/отрицательном значении (не 0), пустые и повреждённые записи отбрасываются. Каталог импортируется/экспортируется JSON-файлом; API валидирует его структуру (422 на некорректную позицию).

`estimate(project)` собирает смету по четырём разделам: «Оборудование» (количество по модели × цена из справочника), «Кабели» (итоговые метры одного кабеля × количество × цена: ручная `cable.pricePerMeter` приоритетнее справочника по марке), «Лотки» (длина по типу трассы × цена) и «Работы» (`Project.estimate.laborPercent` % от стоимости материалов). Итог = материалы + работы. Пустая или отсутствующая цена/количество делают строку, раздел и итог `null` с пометкой «неполная смета»: неизвестное не подменяется нулём. Предупреждения сметы попадают в лист «Предупреждения» и PDF. Выгрузка: XLSX/CSV — листы/разделы «Смета», «Коммерческое предложение» и «Справочник цен»; PDF — секции «Смета» и «Коммерческое предложение».

## Печатные формы PDF

Шрифты PDF — сабсеты PT Sans Regular/Bold (латиница, кириллица, цифры, типографские символы), по требованию OFL переименованы в «AnOOPlan Sans»; это уменьшает APK примерно на 0,6 МБ. Сабсет не содержит редких глифов, поэтому экзотические символы в пользовательском тексте могут не напечататься — базовые кириллица/латиница гарантированы.

`buildJournalPdf(project, fonts, options)` собирает документ в порядке: титульный лист → «Оглавление» → выбранные разделы → планы/фото/предупреждения → итоги и подписи. Титульный лист берёт данные из `Project.document` (организация, объект, шифр, город, заголовок) и подписи «Составил/Проверил»; пустые поля не печатаются как «undefined». Оглавление заполняется после рендера: при выводе заголовка каждой секции запоминается фактическая страница, затем зарезервированная страница оглавления дорисовывается в конце. На каждой странице, кроме титульной, рисуется упрощённый штамп по ГОСТ 2.104 (Изм./Лист/№ докум./Подп./Дата/Разраб./Пров./Т.контр./Н.контр./Утв., обозначение, организация, «Лист N / Листов M»). Лист регистрации изменений печатается из `Project.document.changeLog`.

`JournalOptions.include` — список `JournalSectionId`: `journal`, `equipment`, `cables`, `infrastructure`, `trayFill`, `estimate`, `commercial`, `pins`, `warnings`, `plans`, `photos`, `pinPhotos`, `changeLog`. `undefined` — все разделы; панель «Экспорт / копия» передаёт отмеченные пользователем разделы в печать. Титульный лист и оглавление выводятся всегда.

## Формат .anooplan и обмен

`.anooplan` — JSON-файл проекта (`src/project-file.ts`): `{ format:'anooplan', formatVersion:1, project, pdfs[], photos[], exportedAt }`. `buildAnoPlanFile` собирает файл из проекта и вложений (PDF в base64, фото), `serializeAnoPlanFile` — в JSON, `parseAnoPlanFile` принимает новый формат, прежнюю резервную копию с полем `project` и «голый» JSON проекта, нормализуя проект через миграции; повреждённый файл даёт `ProjectSchemaError`. MIME — `application/vnd.anooplan.project`, расширение `.anooplan`.

Нативная оболочка: `NativeBridge.shareFile(name, base64, mime)` пишет файл в `cache/share`, раздаёт его через собственный `ShareProvider` (`content://com.anooplan.app.share/<имя>`) и открывает системный `ACTION_SEND`-chooser — без androidx FileProvider. Файлы `.anooplan`, открытые через «Открыть с помощью»/«Поделиться», перехватываются intent-фильтрами в манифесте (`VIEW`/`SEND`, MIME `application/vnd.anooplan.project`, а также `file://.../*.anooplan`), читаются в `MainActivity` (лимит 40 МБ) и передаются в интерфейс: `window.__anooplanOpenSharedProject(json)` после `onPageFinished` либо через `takePendingFile()` при монтировании. Интерфейс разбирает файл и загружает проект вместе с PDF и фото; сетевых разрешений у приложения по-прежнему нет.

## API
- GET /api/projects → {id,name,updatedAt}[]
- POST /api/projects тело Project → Project (создание; повтор ID → 409)
- GET /api/projects/:id → Project
- PUT /api/projects/:id тело Project → Project (полная атомарная запись)
- DELETE /api/projects/:id → {ok:true} (удаление проекта и неиспользуемых исходных PDF)
- POST /api/pdfs multipart поле file → {id,name} (исходник PDF)
- GET /api/pdfs/:id → PDF
- GET /api/projects/:id/backup → JSON с project и pdfs:[{id,name,dataBase64}]
- POST /api/restore тело backup → Project (upsert: существующий проект перезаписывается)
- GET /api/health → {ok:true}

`POST /api/restore` проверяет структуру копии и PDF, требует наличия всех исходников в самой копии, выполняет запись PDF и проекта в одной транзакции. Совпадающий ID PDF с другим содержимым даёт 409; проект с тем же ID не конфликтует, а перезаписывается.

## Валидация

`assertProject` в `server/validation.ts` проверяет структуру и ссылки перед записью: `schemaVersion`, уникальность ID, существование этажей, оборудования и сегментов, корректность чисел и режимов. Дополнительно проверяется уникальность номеров оборудования, трасс и кабелей, а для оборудования — уникальность имён. Инженерная неполнота (неизвестный масштаб, отметка или высота, разрывы цепочки) не блокирует сохранение: `validateProject` показывает замечания, а расчёт помечается как неполный.

## Мобильный интерфейс

При ширине до 1023 px панели становятся off-canvas: «Структура» выезжает слева, «Свойства» открываются снизу как шторка; фон затемняется, закрытие — кнопкой или касанием вне панели. Инструменты плана вынесены в нижнюю панель с крупными кнопками, шапка компактная, для свойств есть плавающая кнопка. На десктопе те же панели показаны постоянно по бокам рабочей области.

## Доступность и память рендера

**Системный размер шрифта.** Android WebView не применяет настройку «Размер шрифта» сам, поэтому
`MainActivity` читает `Configuration.fontScale`, округляет до процента и зажимает в 85–160 %
(`textZoomPercent`, зеркало `resolveTextZoom` из `src/a11y.ts`), затем вызывает `WebSettings.setTextZoom`.
Некорректный `fontScale` даёт 100 %. В CSS зафиксировано `text-size-adjust: 100%` (чтобы WebView не
складывал автоувеличение с textZoom), интерактивные элементы используют `min-height` вместо жёсткой
высоты, а длинные подписи переносятся (`overflow-wrap: anywhere`), поэтому крупный шрифт не обрезается.

**Тема и контраст.** Светлая тема — значения `:root`. При `prefers-color-scheme: dark` переменные
поверхностей, текста, границ и теней переопределяются (основной текст на поверхностях — 12,6–16:1),
`color-scheme: dark` включает тёмные системные контролы; план остаётся «бумагой» (белый лист и тёмные
подписи), фон вокруг него тёмный. `prefers-contrast: more` усиливает границы и убирает тени,
`forced-colors: active` не навязывает свои цвета, `prefers-reduced-motion: reduce` отключает анимации.
`<meta name="theme-color">` задан для light/dark по значениям `THEME_COLOR_LIGHT/DARK`.

**Тёмная тема в APK.** WebView определяет `prefers-color-scheme` по теме приложения, а не только по
системному `uiMode`: со светлым `Theme.Material.Light` страница остаётся светлой даже в ночном режиме
(проверено на Android 15). Поэтому в `android/res/values-night/styles.xml` объявлен тёмный `AppTheme`
(`Theme.Material.NoActionBar`), а `uiMode` исключён из `android:configChanges` — смена системной темы
пересоздаёт Activity и подхватывает ночные ресурсы. `fontScale` остаётся в `configChanges`, и
`onConfigurationChanged` заново вызывает `WebSettings.setTextZoom`, поэтому размер шрифта применяется
без перезапуска приложения. Эталон правил масштаба — `src/a11y.ts`; `tests/android-config.test.ts`
сверяет Java, манифест, CSS и ночные ресурсы.

**Поиск, история и клавиатура.** Поиск по спискам — `matchesQuery` из `src/ui/search.ts`:
запрос нормализуется в токены, каждый токен ищется в склеенных полях объекта (номер, тип, наименование,
примечание, подсистема). Пустой запрос совпадает со всем; список показывает «Найдено: N из M».
`Ctrl+K` открывает меню и через событие `cableplan:focus-search` фокусирует поле; на телефоне сайдбар
прокручивается, а поиск закреплён сверху.

История (`src/ui/history.ts` + `use-project-history.ts`) хранит до 100 шагов и **склеивает** изменения
с одинаковой подписью в окне 600 мс: набор числа или текста — один шаг undo. Подписи («Правка поля»,
«Дублирование», «Сдвиг») показываются в подсказках кнопок отмены/повтора. Горячие клавиши: `Ctrl+S`,
`Ctrl+Z`/`Ctrl+Shift+Z`, `Ctrl+K`, `Ctrl+D` (дублировать), `Delete`, `F` (вписать), `1–8` (инструменты),
стрелки — сдвиг выбранного на шаг сетки (Shift — ×10). Копия объекта получает свободный номер
(`uniqueNumber`, «Ш1-копия») и смещение на шаг сетки.

**Мультивыбор и большие списки.** На вкладках Оборудование/Трассы/Кабели/Замечания кнопка
«Выбрать» включает режим массового выбора: строки отмечаются, «Все (N)» выделяет весь отфильтрованный
список, доступны удаление и перенос оборудования/замечаний на этаж. Удаление считает связанные кабели
(`affectedCableIds` в `src/ui/multi-select.ts`) и чистит фото, а вся операция — один шаг undo
(«Массовое удаление»). Списки рисуются порциями по 80 (`pageSlice`) с кнопкой «Показать ещё», поэтому
500+ объектов не создают 500 DOM-строк сразу. Контекстное меню — ПКМ по строке или по объекту на плане
открывает ту же шторку действий, что и долгое нажатие.

**Шаблоны, комплекты и импорт.** `src/templates.ts` хранит четыре встроенных шаблона и
пользовательские в `localStorage` (`cableplan:templates`); при создании проекта шаблон клонируется
без `pdfId`, фото и истории изменений. `src/kits.ts` вставляет набор оборудования на свободное место
этажа и выдаёт следующие номера. `src/catalog-import.ts` разбирает таблицу справочника (RU/EN-заголовки,
цены с пробелами/₽, построчные ошибки) и обновляет позиции по виду+наименованию; `src/catalog-file.ts`
читает XLSX/CSV, загружая `xlsx` отдельным чанком только при импорте. UI-точки — модалка «Новый проект»,
селект комплекта в сайдбаре и предпросмотр импорта в смете.

**Память рендера.** Бюджет подложки — `PLAN_MAX_PIXELS = 8_000_000` (≈32 МБ RGBA) вместо 12 Мпикс:
A4–A3 рисуются целиком, A1/A0 — по видимой области с понижением разрешения; `canvasWidth·canvasHeight`
гарантированно не превышает бюджет (`floor` при округлении). Если полный лист при текущем DPR не
влезает, `planMemoryWarning` формирует предупреждение (лист, мегапиксели, совет «Вписать»), и оно
показывается баннером над планом, а не теряется молча.

## Владение модулями
`src/model.ts` — модель данных (общая для клиента и сервера); схема версионируется, менять осторожно.
`src/engine.ts` — фасад расчётов; реализация в `src/engine/geometry.ts` (длины/запасы/автопрокладка),
`tray-fill.ts` (заполнение), `routes.ts` (сводки), `suggest.ts` (подбор сечения),
`specification.ts` (КНС/сметные формы/валидация).
`src/estimate.ts` — справочник цен, смета по разделам и нормализация каталога.
`src/equipment-icons.ts` — иконки и цвета оборудования (общий набор для плана, PDF и списка).
`src/route-kinds.ts` — типы КНС, цвета по типу/свои, распознавание типа, эффективное сечение участка и подписи сечения (план, список, PDF).
`src/a11y.ts` — эталонные правила доступности (textZoom из системного fontScale, цвета темы) для тестов и нативной оболочки.
`src/ui/segment-editor.tsx` — свойства сегмента: геометрия, запасы и необязательное сечение КНС участка.
`src/App.tsx`, `src/styles.css` — интерфейс; расчёты импортируются из движка и мемоизируются.
`src/sheets.ts`, `src/export-xlsx.ts`, `src/export-pdf.ts`, `src/client-csv.ts` — выгрузки.
`src/project-file.ts` — формат `.anooplan` (сборка/разбор файла проекта); `android/java/.../ShareProvider.java` — раздача файлов для ACTION_SEND.
`src/migrations.ts` — схема и нормализация; `src/idb.ts`, `src/local-projects.ts`, `src/storage-gc.ts` — хранение.
`server/**` — API и SQLite, использует те же модель и движок. `tests/**` — node:test (общие фикстуры — `tests/fixtures.ts`); `eslint.config.js` — стиль и типовые ошибки в CI (`npm run lint`); `scripts/smoke-dom.mjs` — смоук интерфейса.

Проверки: node:test через tsx, сборка tsc + vite, HTTP smoke test и браузерная проверка при наличии Playwright. Проект демонстрации помечен как синтетический, не используется как подмена PDF пользователя.
