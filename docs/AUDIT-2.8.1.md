1. Резюме для владельца проекта
AnOOPlan — технически содержательный проект с зрелым офлайн-контрактом, сильным предметным ядром и необычно дисциплинированным для небольшого приложения набором проверок. В версии 2.8.1 видны результаты предыдущего аудита: исправлены соединение IndexedDB, диагностика квотных ошибок, DPI растровых планов, ограничения импорта, проверка типов при сборке APK и честное разделение метрик покрытия.
Вместе с тем текущий слепок нельзя считать надёжным по полному жизненному циклу пользовательских данных. Наиболее опасен сценарий, в котором пользователь явно выбирает «Сохранить» перед выходом, но приложение закрывается даже после ошибки сохранения. Отдельные операции с фотографиями обходят собственный сборщик мусора и делают undo формальным: ссылка восстанавливается, а бинарный файл уже удалён. Это дефекты не удобства, а основного обещания приложения — «ничего не теряется».
Рекомендуемое решение
Следующую итерацию посвятить патчу надёжности, а не новым функциям. Сначала закрыть F-01…F-08 и добавить интеграционные сценарии на сбои; затем вернуться к дорожной карте 2.8.2/2.9.0. Новые функции не требуют переписывания архитектуры.
Что проверено независимо
277 модульных тестов — все пройдены; 234 smoke-проверки — все пройдены.
ESLint, knip, TypeScript, production build и бюджеты стартового JS/CSS — пройдены.
npm audit — 0 известных уязвимостей в установленном дереве зависимостей.
E2E: 3 из 4 сценариев пройдены; сценарий PDF остановился на имени скачанного файла «download» вместо имени с расширением .pdf.
Точечные воспроизведения подтвердили HTTP 404 серверного экспорта и ложную связность вершин с разной высотой.
Приоритеты в одном абзаце
P0 означает возможную потерю данных в штатном пользовательском действии и требует немедленного исправления. P1 — высокий риск потери/недоступности данных или небезопасный режим эксплуатации; закрывается в том же патче. P2 — ограничение корректности, совместимости, масштабируемости или процесса; планируется следующим этапом. Оценки трудоёмкости: S — до одного дня, M — несколько дней, L — одна-две недели при сохранении существующих интерфейсов.

3. Сильные стороны проекта
Предметная модель и расчёты
Расчёт кабеля не подменяет неизвестную длину или цену нулём: результат помечается неполным, ошибки агрегируются и показываются пользователю.
Проверяются масштаб, отметки этажей, координаты, высоты, дубли идентификаторов, непрерывность цепочки, запасы и количество кабеля.
Дейкстра выбирает путь по физической длине; есть отдельная строгая проверка sameVertex с высотой, хотя граф маршрутизации должен использовать ту же модель.
Офлайн и Android
В манифесте нет разрешения INTERNET; allowBackup=false, debuggable=false, usesCleartextTraffic=false.
WebView отключает файловый доступ, отладка включается только для debug-сборки; ShareProvider не экспортирован и проверяет path traversal.
Нативное сохранение использует MediaStore и IS_PENDING, а выгрузка файлов — системный ACTION_SEND без внешнего FileProvider.
Инженерная дисциплина
CI включает lint, knip, типы, покрытие, сборку, размер, smoke и E2E; GitHub Actions закреплены по SHA.
Релиз подписывает APK, сверяет сертификат и удаляет keystore; production-зависимости разумно ограничены.
Есть миграции проекта, диагностика, снимки, undo/redo, сборщик мусора, документация ARCHITECTURE/HANDOFF/ROADMAP и честные бюджеты.
Стартовый бандл укладывается в заявленные ограничения; тяжёлые PDF/XLSX-модули загружаются по действию.
Вывод по архитектуре
Проект не нуждается в смене стека или переписывании на Kotlin. Требуется довести до конца уже заложенные механизмы владения данными, подтверждения операций и сборки мусора.

5. Детальный разбор находок
F-01. «Сохранить и выйти» может потерять изменения
Параметр
Значение
Приоритет
P0 — критическая
Расположение
src/ui/use-app-effects.ts:59–64; android/java/com/anooplan/app/MainActivity.java:535–588
Доказательство
Подтверждено кодом: два независимых безусловных пути завершения.
Что происходит
При грязном проекте Android предлагает «Сохранить», «Выйти» или «Отмена». После выбора «Сохранить» JavaScript вызывает saveProject(true), но catch лишь пишет диагностику; exitNow() выполняется всегда. Ошибка IndexedDB, localStorage, сервера или квоты поэтому не останавливает выход.
Дополнительно MainActivity через 2500 мс принудительно вызывает finish(), если exiting ещё false. Медленное сохранение большого проекта также приводит к закрытию. Smoke-тест проверяет только успешный путь и поэтому не выявляет дефект.
Ключевой фрагмент
try { await saveProject(true); }
catch (error) { /* выходим в любом случае */ }
nativeBridge()?.exitNow?.();
// MainActivity: postDelayed(... finish(), 2500)
Рекомендации
Закрывать Activity только после явного успешного результата сохранения; при ошибке оставаться на странице и показать повтор, сохранение .anooplan и выход без сохранения.
Убрать безусловный таймер завершения. Таймаут может остановить ожидание, но не должен сам закрывать приложение.
Вернуть из JavaScript результат save-операции через callback/Promise-мост, а не побочный вызов exitNow из общего catch.
Критерий приёмки
Готово, когда
Тесты с rejected saveProject и с сохранением дольше 2,5 с: Activity не закрывается, dirty остаётся true, пользователь видит ошибку и может повторить/выгрузить файл. Успешный путь закрывается один раз.
F-02. Удаление фотографий несовместимо с undo
Параметр
Значение
Приоритет
P1 — высокая
Расположение
src/ui/use-object-actions.ts:52–98, 147–156; src/photos.ts:27–40; src/use-app-effects.ts:50–56
Доказательство
Подтверждено кодом: прямой idbDelete выполняется до оценки живых ссылок.
Что происходит
removeObject, removeMany и removePhoto сразу удаляют Blob из IndexedDB. При этом mutate помещает прежнее состояние в undo. Undo восстанавливает только JSON-ссылку на ключ, но не бинарное содержимое.
Это противоречит собственному контракту GC в use-app-effects: фоновый сборщик специально учитывает текущее состояние, сохранённые проекты, undo/redo и снимки. Прямые удаления обходят все эти проверки. Общий ключ в другом проекте или снимке также теряет файл.
Ключевой фрагмент
mutate(..., 'Удаление');
void purgePhotoBlobs(photoKeys, idbDelete);
 
// removePhoto
mutate(...);
void idbDelete('photo:' + key);
Рекомендации
В операциях, поддерживающих undo, менять только ссылки в проекте. Физическое удаление оставить единому GC после анализа всех живых состояний.
Не создавать второй «быстрый» механизм очистки. orphanPhotoKeys полезен для анализа, но не должен быть основанием для немедленного удаления.
После undo/redo запускать тот же GC с полным набором ссылок; не пытаться восстанавливать Blob отдельно.
Критерий приёмки
Готово, когда
Интеграционный тест: добавить фото → удалить объект → undo → Blob доступен, миниатюра и экспорт работают. Аналогично для removeMany, removePhoto, redo, снимка и двух проектов с общим ключом.
F-03. Серверный экспорт CSV/XLSX/PDF возвращает 404
Параметр
Значение
Приоритет
P1 — высокая
Расположение
src/ui/use-export.ts:74–99; server/app.ts:30–109; README.md:75, 100, 287
Доказательство
Подтверждено запуском: создание проекта 201; export csv/xlsx/pdf — 404 «API endpoint не найден».
Что происходит
В нестатическом режиме buildExportBlob для любого формата, кроме backup, обращается к /api/projects/:id/export. В Express такого маршрута нет; общий обработчик /api возвращает 404.
README прямо указывает, что экспорт выполняется на клиенте, а старый серверный экспорт удалён. Клиентская реализация уже существует ниже в той же функции, но недоступна в серверном режиме из-за раннего return.
Ключевой фрагмент
if (!staticMode) {
  // kind !== 'backup'
  fetch('/api/projects/<id>/export?format=' + kind)
  // => 404
}
Рекомендации
Предпочтительный вариант: использовать единый клиентский CSV/XLSX/PDF во всех режимах, сохраняя проект перед экспортом при необходимости. Это соответствует README и офлайн-архитектуре.
Не восстанавливать второй PDF-движок на сервере. Разные движки дадут расхождения в содержимом и удвоят тестовый контур.
Добавить тест матрицы «Браузер/Сервер» × «CSV/XLSX/PDF/backup/.anooplan».
Критерий приёмки
Готово, когда
В серверном режиме каждый экспорт возвращает ненулевой файл ожидаемого MIME/сигнатуры. Содержимое совпадает с браузерным вариантом на общей фикстуре; тест на исчезнувший endpoint не нужен после удаления ветки.
F-04. Серверный PDF теряет связь с этажом при roundtrip .anooplan
Параметр
Значение
Приоритет
P1 — высокая
Расположение
src/ui/use-export.ts:45–61; src/ui/use-project-io.ts:97–129; src/plan-capture.ts:36–48
Доказательство
Подтверждено кодом: экспортируемый идентификатор и ссылка этажа имеют разные пространства имён.
Что происходит
При экспорте серверного PDF collectProjectArchive сохраняет вложение с id «server:» + исходный id, но project.floors[*].pdfId остаётся исходным. При импорте pdfKeys содержит ключ «server:<id>», а этаж ищет «<id>» — переназначение не происходит.
На том же сервере старая ссылка может случайно продолжить работать и скрыть проблему. На другом сервере или в браузере загруженный PDF остаётся сиротой, а этаж ссылается на недоступный идентификатор.
Ключевой фрагмент
// export
pdfs.push({ id: 'server:' + pdfId, ... });
// import
pdfKeys.set(pdf.id, uploaded.id);
if (pdfKeys.has(stageFloor.pdfId)) { /* нет совпадения */ }
Рекомендации
Хранить в файле исходный логический id без транспортного префикса либо при экспорте согласованно менять и запись вложения, и все ссылки проекта.
При импорте сопоставлять oldId → newId для каждого вложения и обновлять все ссылки атомарно; префикс хранилища формировать только на границе адаптера.
Добавить сквозной тест «сервер A → .anooplan → браузер/сервер B» с фактическим чтением страницы PDF, а не только проверкой массива pdfs.
Критерий приёмки
Готово, когда
После roundtrip floor.pdfId указывает на новый загруженный Blob; capturePlanPages успешно открывает документ. В архиве нет неиспользуемых дублей и неразрешённых ссылок.
F-05. Неполная резервная копия выглядит успешной
Параметр
Значение
Приоритет
P1 — высокая
Расположение
src/ui/use-export.ts:41–71, 95–99, 133–151; server/app.ts:70–76; server/app.ts:77–97
Доказательство
Подтверждено кодом: missing/ошибки вложений отбрасываются; серверный backup не содержит photos.
Что происходит
Если IndexedDB не вернула PDF, fetch завершился неуспешно или чтение фото выбросило ошибку, collectProjectArchive просто продолжает. buildAnoPlanBlob и JSON backup затем сообщают об успешном формировании файла без списка пропущенных вложений.
Серверный /backup возвращает project и pdfs, но не photos, хотя проект хранит ссылки на них. /api/restore также обрабатывает только PDF. Поэтому серверная JSON-копия не является полной копией фотографий.
Ключевой фрагмент
if (pdfBlob) pdfs.push(...); // иначе молча пропуск
if (!response.ok) continue;
catch { /* фото недоступно — копия всё равно выгружается */ }
// warning: ''
Рекомендации
Собирать manifest ожидаемых вложений: логический id, тип, размер, MIME, SHA-256. Сверять фактический набор до объявления успеха.
По умолчанию прерывать backup при отсутствии вложений. Неполный файл допускать только после явного подтверждения с видимой пометкой incomplete и списком потерь.

Готово, когда

Параметр
Значение

Расположение

Доказательство
Подтверждено кодом: импорт переиспользует photo.key, deleteProject удаляет Blob без анализа других ссылок.

Готово, когда

F-09. Маршрутизатор соединяет вершины с разной высотой
Параметр
Значение
Приоритет
P2 — средняя
Расположение
src/engine/geometry.ts:13–15, 93–164, 227–247
Доказательство
Подтверждено запуском: findRoute вернул [s1,s2], calculateCable — complete=false и ошибку разрыва.
Что происходит
Ключ графа включает floorId, x и y, но не height. Две точки на одном этаже с одинаковыми X/Y и высотами 3 м и 6 м сливаются в одну вершину. Дейкстра находит через них путь, хотя физического соединения нет.

const key = (floorId, x, y) =>
  floorId + '|' + x.toFixed(3) + '|' + y.toFixed(3);
const weightOf = s => segmentLength(...) === null ? 1 : ...;
Рекомендации
Включить нормализованную высоту в идентичность вершины либо строить узлы по vertex.id с явными правилами эквивалентности.
Не добавлять в граф сегменты с segmentErrors/неизвестной длиной; сообщать, почему маршрут невозможен, вместо фиктивного веса 1.
Использовать одну функцию эквивалентности для построения графа и проверки цепочки.
Критерий приёмки
Готово, когда

6. Архитектурные рекомендации
Архитектурная цель следующего патча — не увеличить число абстракций, а сделать невозможными противоречивые операции с данными. Сейчас общий GC спроектирован правильно, но несколько вызовов обходят его; экспорт имеет два разных поведения; идентификаторы хранилища смешиваются с переносимой моделью. Это следует закрыть узкими сервисами с понятными инвариантами.
6.1. Единый AttachmentService
Владеть отображением logical attachment id ↔ конкретное хранилище: idb:, server id, data:. Предметный проект не должен зависеть от префикса транспорта.
Предоставить операции collect, verify, importWithRemap, references и collectGarbage. Все экспортёры и удаления используют только их.
Инвариант: физический Blob удаляется только после доказательства отсутствия ссылок во всех живых состояниях.
6.2. Единый ExportService
Один клиентский генератор CSV/XLSX/PDF для браузера, APK и серверного хранения. Режим хранения влияет на save/load, но не на содержимое документа.
Сборка архива возвращает не только Blob, но и manifest/warnings. Сообщение «сохранено» формируется после проверки полноты и результата записи на устройство.
Для больших данных интерфейс должен допускать потоковую/чанкованную реализацию без изменения UI.
6.3. Явные результаты операций
saveProject, takeSnapshot, saveAndExit и restore возвращают успех/ошибку; пустой catch запрещён на критических путях.
UI подтверждает только фактически завершённую операцию. При восстановлении старой версии сначала гарантируется сохранность текущей.
6.4. Точечная декомпозиция без переписывания
src/export-pdf.ts содержит 812 строк, MainActivity.java — 611; useWorkspaceState компактен по строкам, но объединяет десятки состояний и широкий фасад. Рекомендуется выделять PDF page-kit/sections, Android save-exit coordinator и чистые project use-cases постепенно, сохраняя публичные фасады и прогоняя существующие тесты после каждого шага. Отдельный масштабный рефакторинг не должен блокировать исправления P0/P1.
7. Стратегия регрессионных проверок
Высокое покрытие импортируемых модулей не выявило главные дефекты, потому что они находятся на стыках React-хуков, IndexedDB, сервера и Android. Следующий прирост качества даст не погоня за процентом, а небольшой набор интеграционных тестов с отказами и реальными Blob.

Доказательство
Подтверждено запуском на 360×800 и чтением кода. После открытия экспорта фокус остаётся на кнопке «Экспорт / копия»; aria-modal отсутствует. Значение
Эффект

Значение

UX-09 · P2 · Выбранные состояния и скрытые действия недостаточно обозначены
Параметр
Значение
Эффект
Слабая обратная связь и discoverability
Доказательство
Подтверждено кодом: активные view-tabs, structure-tabs и инструменты отмечены только className="active", без aria-current/aria-pressed. Действия объекта открываются контекстным меню или длительным нажатием; видимой кнопки «…» в строке нет.

UX-10 · P3 · Иконографика и визуальные ритмы не полностью систематизированы
Параметр
Значение
Эффект

Доказательство
В интерфейсе смешаны текстовые стрелки, геометрические символы и emoji: ↖, ✥, ⌁, ⟷, 📏, 📍, 🗑, 🎓. Их форма и базовая линия зависят от платформенного шрифта.
Общая графитово-бирюзовая стилистика спокойная и подходит рабочему чертежу, но смешанные иконки выглядят непоследовательно. Маленькие uppercase-подписи 10–12 px усиливают плотность.
Перейти на единый локальный SVG-набор 20/24 px с постоянными stroke/fill; не загружать внешний icon CDN в офлайн-приложении.
Сохранить текстовые подписи у неоднозначных инструментов; emoji оставить только как содержательный маркер, не как системный контрол.
Зафиксировать spacing 4/8/12/16/24, типографические роли и состояния в небольшой UI Style Guide; провести визуальный аудит без изменения предметных цветов плана.
Критерий приёмки
Одинаковые действия имеют одинаковые иконки на Android и desktop; baseline, размеры и hit areas совпадают. Визуальные снимки светлой/тёмной темы проходят review.

11. Заключение
AnOOPlan уже имеет крепкую основу: офлайн-ограничения реализованы последовательно, расчётное ядро осторожно обращается с неизвестными значениями, Android-оболочка компактна, а CI заметно превышает типовой уровень небольших внутренних инструментов. Независимый запуск подтвердил качество большей части существующих проверок.
Главный резерв — согласованность между подсистемами. Сборщик мусора знает об undo, но прямые удаления его обходят. Клиентский экспорт существует, но серверный режим вызывает удалённый API. PDF переназначается при импорте, но префикс серверного экспорта ломает сопоставление. История обещает сохранить текущее состояние, но скрывает ошибку записи. Это не требует новой платформы — требуется единый контракт владения данными и подтверждения операций.
Итоговая рекомендация
Выпустить небольшой патч надёжности, затем провести UX-итерацию без смены платформы. После закрытия F-01…F-08 и UX-01…UX-05 проект можно уверенно развивать по существующей архитектуре и дорожной карте.
