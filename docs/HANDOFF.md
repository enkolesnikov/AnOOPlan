# Контекст-хендофф: AnOOPlan

Документ для продолжения работы в новой сессии. Прочитайте его целиком перед первым действием.
Секретов здесь нет: токены и пароли передаются отдельно и в репозиторий не попадают.

## Что это за проект

**AnOOPlan** — приложение для раскладки кабельных трасс по PDF-планам здания и расчёта кабельного
журнала. Основной продукт — **офлайн-APK для Android**; та же кодовая база собирается как веб-версия
на GitHub Pages. Выросло из веб-приложения [ooplan](https://github.com/enkolesnikov/ooplan) (CablePlan).

- Репозиторий: <https://github.com/enkolesnikov/AnOOPlan>
- Релизы с APK: <https://github.com/enkolesnikov/AnOOPlan/releases>
- Веб-версия: <https://enkolesnikov.github.io/AnOOPlan/> — та же сборка, что и APK; публикуется
  вручную по запросу (приоритет — Android).
- Текущая версия: **2.0.0**, versionCode 28, `com.anooplan.app`, minSdk 24, targetSdk 35.
  APK ~1,8 МБ, WebView 98+, 190 юнит-тестов + 200 проверок смоука + 2 E2E.
- Возможности: PDF-планы и калибровка, оборудование с иконками и цветом, трассы, кабели и автопрокладка,
  журнал, справочник цен и смета с коммерческим предложением, печатные формы (титул, оглавление,
  штамп ГОСТ, лист изменений), печать выбранных разделов, обмен PDF/XLSX и проектом `.anooplan`,
  XLSX/PDF, история версий, фото, пины-замечания с фото, проверка заполнения лотка.
- **Курс — Android-first.** Облако — в планах (дальняя перспектива); приложение полностью офлайн,
  разрешение `INTERNET` не запрашивается, сетевых модулей нет.
- Подпись: SHA-256 сертификата `6431374cf6a7d385c4c47f0f2bf54fcb5ee5b2c7120f057b18c4062af92fe097`.
- Текущий релиз: **v2.0.0 «оптимизация Android»** — подписанный APK `AnOOPlan-2.0.0.apk`
  (versionCode 28) и описание из аннотации тега.

## Режимы работы

| Режим | Где используется | Хранение |
|---|---|---|
| **Браузер / APK** (основной) | APK и GitHub Pages | Проекты — `localStorage`, PDF/фото/снимки — IndexedDB |
| **Сервер** (вспомогательный) | `npm start`, локальная веб-версия | SQLite (`node:sqlite`) + PDF в `data/` |

APK всегда работает в режиме «Браузер»: запрос `/api/health` получает 404, приложение включает
`staticMode`. Серверная часть остаётся для локального веба и не входит в APK. Веб-версия — это та же
статическая сборка; на GitHub Pages она публикуется вручную (`deploy.yml`, `workflow_dispatch`).

### Ключевые решения (не пересматривать без причины)

1. **WebView вместо Kotlin-переписывания.** Одна кодовая база для сайта и APK, 190 тестов, быстрые
   итерации. Kotlin оправдан только при ежедневной работе пером и листах A1+ — тогда начинать
   с порта `engine.ts` в KMP, а не с UI.
2. **Статика отдаётся по origin `https://appassets.local/`** через `AssetServer.shouldInterceptRequest`.
   На `file://` не работают IndexedDB и `crypto.randomUUID()`. Запросы `/api/*` получают 404 →
   включается `staticMode`.
3. **Всё офлайн.** Разрешение `INTERNET` не запрашивается. Никаких сетевых вызовов в APK нет.
4. **Экспорт на клиенте.** XLSX и PDF собираются на телефоне; печать — `PrintManager` с готовым PDF
   в спулер без растеризации. Файлы сохраняются через MediaStore, без опасных разрешений.
5. **Подпись.** `keystore/anooplan.jks` (в `.gitignore`), пароль в `keystore/pass.txt` (0600, вне git).
   Пароль не хранится в скриптах; `scripts/build-apk.sh` читает `keystore/pass.txt` или `KS_PASS`.
   GitHub Secrets: `ANDROID_KEYSTORE_BASE64`, `ANDROID_KS_PASS`, `ANDROID_KS_ALIAS`,
   `ANDROID_CERT_SHA256`.
   **Важно:** в сессии 2026-10 на VPS сгенерирован новый ключ (оригинальный в репозиторий не входит).
   APK с 1.6.1 подписаны им; обновление поверх 1.6.0 требует переустановки (сначала сохранить проект
   в JSON). Если появится оригинальный keystore — положить его в `keystore/anooplan.jks`, заменить
   пароль и пересобрать релиз.
6. **Автобэкап выключен** (`allowBackup="false"`): проекты могут содержать планы заказчика.
   Перед переустановкой/удалением приложения пользователь должен сохранить JSON-копию.
7. **История и GC.** Снимки проектов (до 20 на проект) лежат в IndexedDB. Фоновый GC удаляет
   PDF/фото, на которые больше не ссылаются текущий проект, undo/redo, сохранённые проекты и снимки.
   Снимки удалённых проектов тоже вычищаются.
8. **Заполнение лотка (1.15.0).** Считается по площади: `Sкаб = crossSectionMm2` или `π·d²/4`,
   `Sлотка = trayAreaMm2` или `trayWidthMm·trayHeightMm`, заполнение сегмента =
   `Σ(Sкаб · quantity) / Sлотка · 100`. Площадь всегда приоритетнее диаметра/размеров; неизвестные
   данные дают `null`/«не рассчитано», а не 0. Пороги: > 40 % — внимание, > 50 % — превышение.
   Размеры лотка — на трассе (не на сегменте): все сегменты трассы используют один лоток.
   `specifications().trayFill` — одна строка на сегмент для ведомости/PDF/XLSX/CSV.
9. **Иконки и цвет оборудования (1.16.0).** Иконка выводится из типа: `equipmentIcon(type)` ищет
   «камер/шкаф/розет/коммутатор/считыв», иначе — универсальный маркер. Геометрия `EQUIPMENT_ICON_GLYPHS`
   в системе 24×24, заливка цветом с `fill-rule="evenodd"` (отверстия объектива/окна/гнёзд — сквозные);
   один набор используется в `App.tsx`, списке объектов и `plan-svg.ts` (PDF-лист «План»).
   `Equipment.color` — необязательный `#rrggbb`; `equipmentColor()` при невалидном/пустом значении берёт
   цвет по умолчанию для типа (`EQUIPMENT_ICON_DEFAULT_COLORS`), значит подмена безопасна и видима.
   Миграции нормализуют цвет (`#rgb` → `#rrggbb`, мусор → `undefined`), API отклоняет мусор с 422.
10. **Справочник цен и смета (1.17.0).** Справочник (`Project.catalog`) — часть проекта, а не глобальный
    файл: поэтому он входит в JSON-копию, снапшоты и офлайн-хранилище, и старые снимки сохраняют свои
    цены (смена прайса не пересчитывает историю). Смета: оборудование — количество по модели × цена;
    кабели — итоговые метры × количество × цена (ручная `pricePerMeter` приоритетнее справочника по
    марке); лотки — длина по типу трассы × цена; работы — `laborPercent` % от материалов; итог =
    материалы + работы. Любая неизвестная цена/величина делает строку, раздел и итог `null` с пометкой
    «неполная смета» — неизвестное не подменяется нулём. Дата прайса (`catalogDate`) печатается в смете
    и КП. Схема осталась v2: новые поля необязательны и нормализуются при загрузке.
11. **Печатные формы и обмен (1.18.0).** PDF-документ начинается с титульного листа и «Оглавления»
    (страницы оглавления заполняются после рендера по фактическим номерам), на каждой странице кроме
    титула — упрощённый штамп по ГОСТ 2.104, в конце — лист регистрации изменений из
    `Project.document.changeLog`. `buildJournalPdf({ include })` печатает только выбранные разделы;
    титул и оглавление — всегда. Проект можно отдать одним файлом `.anooplan`
    (`src/project-file.ts`): JSON с проектом, PDF и фото; старые backup-копии тоже открываются.
    Обмен — через нативный `ACTION_SEND` и собственный `ShareProvider` (сборка без androidx);
    intent-фильтры `VIEW`/`SEND` открывают `.anooplan` из файлового менеджера, MainActivity читает
    файл и передаёт JSON в `window.__anooplanOpenSharedProject`.
12. **Android-first (2.0.0).** Приложение полностью офлайн, `INTERNET` не запрашивается, сетевых
    модулей в коде нет. Сетевые функции не добавлять без отдельного решения владельца.
13. **Веб-версия — вручную (2.0.0).** Автодеплой Pages на каждый push выключен: он тратил ~62 с
    runner-времени и дублировал тесты, а APK использует ту же статическую сборку. Публикация —
    `workflow_dispatch` в `deploy.yml`; аналогично неподписанный APK — `android-apk.yml` вручную.
14. **Версия — единый источник (2.0.0).** `package.json`: `version` и `androidVersionCode`;
    `scripts/build-apk.sh` читает их оттуда, `AndroidManifest.xml` содержит те же значения и проверяется
    тестом. Не заводить третьи копии версии.
15. **Скриншоты на каждый релиз: 1–3 (минимум один).** Прикладывать к GitHub Release (assets/описание)
    и показывать в отчёте сессии; для невизуального изменения — один скриншот подтверждения.

## Команды

```bash
npm ci                      # зависимости (Node 22.5+, проверено на Node 24)
npm test                    # 190 тестов (движок, лоток, иконки, смета, формы, миграции, API, экспорт)
npm run test:ui             # сборка + Playwright E2E с реальным PDF
npm run smoke               # смоук интерфейса (happy-dom, 200 проверок), включая заполнение лотка
npm run build               # tsc --noEmit + vite build
bash scripts/fetch-tools.sh # platform-35, build-tools 35.0.0, r8.jar
npm run build:apk           # подписанный APK в build/AnOOPlan-<версия>.apk
UNSIGNED_APK=1 npm run build:apk  # выровненный неподписанный APK (артефакт, вручную)
# Версия и versionCode берутся из package.json: version + androidVersionCode.
npm start                   # локальный сервер: API + сайт на :3001
```

Для сборки APK нужны **JDK 17**, `zip`, `python3` и `node`. `fetch-tools.sh` скачивает только
Android-инструменты; JDK на VPS уже установлен. Если `keystore/` нет, обычная сборка остановится:
ключ не должен генерироваться случайно. Первая локальная сборка без ключа:
`ALLOW_NEW_KEYSTORE=1 bash scripts/build-apk.sh` — создаст новый ключ и `keystore/pass.txt`.
Для существующего продукта это означает новую подпись и переустановку у пользователей.

Сборка на VPS уже подготовлена: JDK 17, Android SDK в `/root/android-sdk`, build-tools 35 в
`tools/build-tools/35.0.0`, platform jar в `tools/android.jar`, AVD `AnOOPlan35`, Chromium Playwright
в `~/.cache/ms-playwright`. `adb` — `/root/android-sdk/platform-tools/adb`.

## CI и релиз

- `.github/workflows/ci.yml` — обязательный прогон на каждый push/PR: `npm ci`, `tsc --noEmit`,
  тесты, смоук, E2E. Это единственный автоматический workflow; держать его ≤110 с.
- `.github/workflows/android-apk.yml` — **вручную** (`workflow_dispatch`): неподписанный APK
  (`AnOOPlan-apk-unsigned`) для проверки установки. Ключ в раннере не создаётся.
- `.github/workflows/deploy.yml` — **вручную** (`workflow_dispatch`): публикация веб-версии на Pages.
- `.github/workflows/android-release.yml` — по тегу `v*`: тесты, смоук, E2E, подписанный APK
  из GitHub Secrets, проверка SHA-256 сертификата, GitHub Release (описание берётся из аннотированного
  тега через GitHub API — checkout делает локальный тег облегчённым; есть fallback на локальную
  аннотацию и сообщение коммита), удаление keystore с раннера.

Порядок релиза:

1. Поднять версию: `version` и `androidVersionCode` в `package.json` (единственный источник),
   затем те же значения в `android/AndroidManifest.xml` — тест проверяет совпадение; `build-apk.sh`
   берёт версию из `package.json`.
2. Обновить `README.md` и этот файл, прогнать `npm test`, `npm run smoke`, `npm run test:ui`, `npm run build`.
3. Снять **1–3 скриншота изменений** (минимум один) на эмуляторе/в Chromium; сохранить в
   `build/release-screenshots/` (git не трогаем).
4. Закоммитить и запушить `main`; дождаться зелёного CI (`ci.yml`).
5. Поставить **аннотированный** тег `vX.Y.Z` с описанием изменений и запушить его — релиз соберёт
   workflow, а сообщение тега станет описанием GitHub Release (поэтому не пустой `Full Changelog`).
6. Приложить 1–3 скриншота к опубликованному Release (assets и/или описание) и проверить, что в
   GitHub Release есть APK и сертификат совпал с `ANDROID_CERT_SHA256`.
7. После релиза — обновить HANDOFF (состояние, ссылка на релиз) и, при необходимости, вручную
   опубликовать веб-версию (`deploy.yml`).

Локальная подпись: `KS_PASS=... bash scripts/build-apk.sh` или пароль из `keystore/pass.txt`.
Не коммитить `keystore/`, `build/`, `tools/`, `android/assets/`, `.env` и любые токены.

## Данные, хранение и диагностика

- Проекты: `localStorage` `cableplan:projects`; черновик — `cableplan:autosave`.
- PDF и фото: IndexedDB `cableplan`, хранилище `pdfs`; PDF — ключ без префикса, фото — `photo:<key>`.
- Пины: массив `project.pins` в JSON, фото пинов — те же `photo:<key>`, что у оборудования.
- Снимки: хранилище `snapshots`, ключ `<projectId>:<timestamp>`, максимум 20 на проект.
- Диагностика: `cableplan:diagnostics`, до 50 записей, экспорт в текстовый файл.
- GC запускается через 3 секунды после изменений и учитывает undo/redo и снимки. Поэтому старый блоб
  может оставаться, пока на него ссылается история; это защита undo, а не утечка. После перезапуска
  приложения история очищается, и сироты удаляются, если на них не ссылаются снимки.
- `schemaVersion: 2`: в v2 добавлены пины. Миграция `v1 → v2` в `src/migrations.ts`; проекты
  из будущей версии отклоняются. В 1.15.0 схема не менялась: поля `outerDiameterMm`/`crossSectionMm2`
  у кабеля и `trayWidthMm`/`trayHeightMm`/`trayAreaMm2` у трассы необязательны и нормализуются при
  загрузке (мусор → `undefined`, не 0; 0 и отрицательные сохраняются и ловятся валидацией).
  В 1.16.0 схема тоже не менялась: `Equipment.color` (необязательный `#rrggbb`) хранится в JSON
  оборудования и нормализуется при загрузке, как и остальные новые поля. В 1.17.0 добавлены
  `Project.catalog` (справочник цен), `Project.catalogDate` и `Project.estimate`; они необязательны,
  нормализуются при загрузке и входят в снапшоты/JSON-копию. В 1.18.0 расширен `Project.document`
  (титульный лист и `changeLog`) — тоже необязательные поля, нормализуемые при загрузке;
  `.anooplan` содержит те же данные, что резервная копия, плюс маркер формата.
  Ревизии сущностей и облачная синхронизация — в планах; в текущей схеме их нет.

## Известные проблемы и техдолг

**P0** — открытых нет.

**P1 (план 2.1.0)**
- `App.tsx` 1 489 строк: экраны и служебные компоненты (`EstimateScreen`, `SpecificationTables`,
  `IssueList`, `EquipmentIcon`, `NumberField`) внутри — вынести по файлам, цель <500 строк.
- `xlsx` 0.18.5: high без фикса в npm; используется на запись и в тестах. Заменить на ExcelJS или
  официальную сборку SheetJS с паритетными тестами.
- Легаси-серверный экспорт `server/export.ts` + `pdfkit` (≈5,9 МБ, системные TTF) дублирует клиентский
  экспорт — удалить, оставив локальному серверу только CRUD.
- Дубли фикстур проекта в 12 тестах; нет `tests/fixtures.ts`.
- Нет бюджетов покрытия/размера бандла в CI и `npm run status`; счётчики в документации правятся руками.
- UI-хуки (`useProjectHistory`, `useSnapshots`, `usePdfBackground`) без прямых тестов.
- Доступность: основные `aria-label`, фокус, reduced-motion и текстовая альтернатива canvas уже учтены;
  `textZoom(100)` по-прежнему игнорирует системный размер шрифта, нет тёмной темы/высокого контраста.
- Память: 12 Мпикс ≈ 48 МБ на канву; для бюджетных телефонов разумнее 6–8 Мпикс с предупреждением.
- Подмножество PT Sans уменьшит APK примерно на 0,6 МБ.
- Реальная проверка WebView 98 не проводилась (тестировали 124); на userdebug-эмуляторе Android 15
  devtools-сокет WebView остаётся доступен даже при `debuggable=false` — это особенность отладочной
  сборки ОС, не APK. На пользовательских сборках отладка выключена.

**P2**
- Векторный план в PDF вместо растра 1600 px.
- Сравнение снимков версий (diff).
- Неиспользуемые стили `.export-menu` в `styles.css`.
- Диагностика: показывать занятое место и версию WebView в интерфейсе, а не только в экспорте.
- Заполнение лотка считается по площади внешнего сечения без коэффициента укладки/пучков и без учёта
  радиуса изгиба; для плоских кабелей нужен явный ввод площади. Размеры лотка задаются на трассу,
  а не на сегмент: если в одной трассе разные лотки, нужен сегментный override (пока не сделан).
- Заполнение в ведомостях показывается по сегментам, но `warnings` сегментов не дублируются
  в таблице (видны в свойствах трассы и в общем списке предупреждений).
- Иконки оборудования фиксированы (6 типов, маппинг по подстроке типа): нет загрузки своих SVG
  и переопределения иконки независимо от типа. Цвет — только `#rrggbb` (палитра или пикер),
  в XLSX/PDF-ведомость цвет не выводится — только на план.
- Смета не учитывает НДС, наценку, доставку и разные единицы измерения кроме «шт» и «м»; работы —
  только процент от материалов, без отдельных видов работ. Каталог привязан к проекту, общего
  справочника между проектами нет (обмен — только JSON-файлом).
- Печатные формы упрощены: штамп по ГОСТ 2.104 не является полной формой 2/2а (нет граф заказчика,
  согласований и масштаба), изменение листа не отслеживается автоматически — `changeLog` заполняется
  вручную. Оглавление всегда занимает одну страницу; очень длинный документ (>14 разделов) может
  потребовать второй страницы, которая пока не поддерживается.
- `.anooplan` с вложенными PDF ограничен по размеру (MainActivity читает до 40 МБ); формат версионируется
  полем `formatVersion`, но обратная совместимость будущих версий не обещана.
- ACTION_SEND/«Открыть с помощью» проверяются на эмуляторе вручную; автоматического Android-теста
  этих сценариев нет.

### Kotlin и онлайн: принятые выводы

- **Kotlin-переписывание сейчас не оправдано.** Основные риски — релиз-инженерия, тесты и
  обработка ошибок, а не WebView. Переписывание даст 3–6 месяцев до паритета и вторую кодовую базу.
  Пересматривать, если станет критичным стилус, ежедневные A1/A0 или WebView начнёт блокировать
  развитие. Промежуточный вариант — вынести в Kotlin только растеризацию PDF.
- **Сетевые функции — только по отдельному решению.** Офлайн-режим остаётся полноценным; PDF/фото
  живут на устройстве.

## Правила для новой сессии

- Начинать с чтения этого файла и `README.md`, затем `npm ci && npm test && npm run smoke`.
- **Курс — Android-first.** Не добавлять сетевые вызовы и `INTERNET` без отдельного решения владельца.
- **Не коммитить**: `keystore/`, `tools/`, `build/`, `android/assets/`, ключи, токены, `.env`.
- Перед пушем: `tsc`, тесты, смоук и E2E зелёные; версия/`versionCode` — только в `package.json`
  (и те же значения в манифесте, их проверяет тест); README и HANDOFF обновлены.
- Релиз — только через аннотированный тег `vX.Y.Z` и `android-release.yml`; приложить **1–3 скриншота**
  изменений к GitHub Release и показать их в отчёте сессии.
- Бюджеты: CI на push ≤110 с, стартовый бандл ≤450 КБ, APK ≤1,4 МБ с 2.1.0, 0 high-уязвимостей
  с 2.1.0. Счётчики в документации вручную не синхронизировать — с 2.1.0 это делает `npm run status`.
- Автодеплой Pages и неподписанный APK на push не включать: только `workflow_dispatch`.
- Не менять политику устройства (DSHA) и не пытаться обойти блокировки доступа.
- Секреты (токен GitHub, ключ DeepSeek, пароль keystore) приходят отдельно; в файлы репозитория
  их не писать.
- Если код расходится с этим документом — сначала проверить факты в коде, затем обновить документ.
